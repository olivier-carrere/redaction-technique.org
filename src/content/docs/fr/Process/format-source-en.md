The content of a **technical writing** project is created in a source format, different from the format of the deliverables, the target format. To use an image frequently used in software development, the source format is the recipe, the target format the dish. In photography, the source format is the RAW format, which is generated by the camera, and on which professional photographers prefer to carry out retouching, and the target format, the JPEG format.

Word processors have unaccustomed us to distinguishing between form and content. But confusing the two leads to many errors and wasted time.

In fact, the document presented to the user has two fundamental aspects:

* content,
* layout.

During the development of technical documentation, these two aspects must be clearly distinguished. They can be handled by two different people:

* the **technical editor**,
* the graphic designer.

When the layout is as important as the content, or when it must be varied, as in the case of a sales brochure, writing and layout are carried out using different tools:

* text editor,
* DTP software such as InDesign or Scribus.

When the layout is less important than the content, or when it needs to be homogeneous, as in the case of a **technical documentation**, editing and layout are carried out on :

| File type | Example |
| ----------------------- | ---------------------------------------------------------------------- |
| For example, **FrameMaker** files.                              |
| Different files | For example, XML content files and an XSLT stylesheet. |

In a **FrameMaker** file, the separation of content and form is high, but not total: content and layout are placed in the same file. **FrameMaker** applies a uniform page layout to an entire file, but allows layout elements to be added manually. The same layout can be duplicated for the entire document, or a different layout can be used for each file making up the document.

Source formats can be classified according to their degree of modularity and file format.

The structured XML formats **DocBook** and **DITA XML** apply a homogeneous page layout to an entire document, and do not allow the manual addition of layout elements, nor the application of different layouts to the different files that make up the document.

| Format | Manual layout options
| ---------- | ------------------------------------ |
| MS Word | Yes |
| FrameMaker | Yes |
| DITA XML | No |

If content and layout are intimately linked, as in a word processor, it's difficult to modify the content without disturbing the layout. As a result, each time a new version of technical documentation is published, the **technical writing** team spends long hours correcting layout errors generated by the software. This phenomenon is less common with **FrameMaker**, but is still significant. It is non-existent with **DITA XML** and **DocBook** (the only errors that can occur are compilation errors due to incorrect XML syntax; these are easily rectified).

Technical documentation source files are in :

* binary or,
* text format.

This format is also :

* WYSIWYG or,
* structured.

Finally, this format is :

* modular or,
* monolithic.

This last aspect determines how the format handles single-sourcing:

* according to a book-to-online-help logic or,
* online help to book.

The available formats can therefore be classified according to the following table:

| Structured format | Manual layout option | Manual layout option
| ---------------- | ------------------------------------ |
| FrameMaker | No |
| DocBook | Yes |
| DITA XML | Yes |

**FrameMaker** and **DocBook** are not fully modular, as the smallest elements of information that can be manipulated are not generic: they contain information such as table of contents structure or cross-references that are only valid in a limited number of contexts.

## Monolithic or modular documents

The source format can be based on monolithic files or on clusters of modular files.

Monolithic files (e.g. **MS Word**, **LibreOffice** or **FrameMaker**) centralize all content in a single, easy-to-handle file, but limit content sharing; the risk of inconsistent or duplicate information is then significant.

![Monolithic technical writing source format](/assets/monolithic.svg)
**Monolithic technical writing source format** (/assets/monolithic.svg)

Modular file clusters (e.g. **DITA XML**) aggregate the content of multiple files, enabling content blocks to be shared and reused. Such a system is difficult to implement company-wide, but should be the norm for a **technical writing** team.

![Modular technical writing source format](/assets/grappe.svg)
**Modular technical writing source format** (/assets/grappe.svg)

Some word processors can handle modular documents, but they don't do it very well. Conversely, a **DocBook** or **DITA XML** document, for example, can be monolithic, but then loses its flexibility.

### Markdown as a source format

A modern source format widely used in **technical writing** is **Markdown**. It's a lightweight, human-readable text format that clearly separates content from formatting.

For example:

* Headings are indicated by `#`, not by visual styles.
* Lists are marked with `-` or `*`, not graphic bullets.
* Bold or italic text is framed by `**` or `_`.

Markdown offers several advantages for technical writing:

1. **Simplicity**: it's easy to learn and use.
2. **Modularity**: each Markdown file can be a stand-alone information module.
3. **Interoperability**: text files can be converted to HTML, PDF, DocBook, DITA, or even Word, thanks to generators such as Pandoc.
4. **Traceability**: as the files are plain text, they lend themselves perfectly to versioning with Git or other source control systems.

Markdown enables structured, reusable content to be produced, while remaining simple and accessible to technical writers. It lies between conventional word processing (WYSIWYG, but not very modular or structured) and XML (modular and structured, but complex to manipulate).

### What is an information module?

The world's best-known modular system is certainly that of the Lego bricks. Adapted to technical documentation, the module principle helps to improve the quality of technical manuals and the productivity of technical writers.

But is it enough to convert FrameMaker documentation to a structured format such as DITA XML or Markdown to obtain modular documentation? Unfortunately not. If the original content is a mixture of all kinds of information (concepts, step-by-step procedures, references), it will always be possible to convert it to Markdown or DITA XML without strictly respecting the semantics of the format.

However, if you end up with a document based on files each corresponding to a different schema (concept, task or reference), you don't necessarily end up with truly modular documentation. In fact, if you try to build a document containing only files of a single type, your document is likely to be incomplete and incoherent.

This documentation is not modular, because it is not based on real information modules. A module is a complete and coherent atomic element that can be reused in different contexts. If you've divided your original monolithic document into a multitude of files, you haven't yet created any information modules. The second step is to rewrite each file (using the minimalist approach, for example) to make it more generic and a genuine module.

Of course, it's important to adopt a structuralistic approach and decide on the content of each module from the perspective of the overall document architecture. Similarly, references such as "See next section" should be replaced by cross-references. Ideally, these cross-references should not be located in the content files themselves, but in a relative section specific to each ditamap file.

In this way, modules are perfectly decontextualized, and structural information such as cross-references are placed in files with no textual content.

## Binary or text files

Source formats are binary or text.

* Binary formats are *opaque*: if you open them with a text editor such as *Notepad*, all you see is a series of hieroglyphic characters, so it's usually only possible to modify them with a single program.
* Text formats are *transparent*: if you open them with a text editor, you see text and tags; it is therefore possible to modify them with different software and apply batch processing operations on the command line, without even opening them, and to use powerful regular expressions.

**Markdown** is a perfect example of a transparent, simple, modular and easily traceable text format.
