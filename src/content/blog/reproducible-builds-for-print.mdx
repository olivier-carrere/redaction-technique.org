## The commit hash is necessary but not sufficient

A Git commit hash identifies a source snapshot. It answers: *what text went in?* But for a printed book, that question isn't complete. A PDF is the product of source *and* environment — the LaTeX engine, the font renderer, the OS-level libraries, the specific build of the toolchain. Two identical source trees, compiled by two different LuaTeX versions, can produce different output.

Not dramatically different. Not wrong, exactly. But different in ways that matter: subtly shifted line breaks, marginally different hyphenation, page counts that drift by one. When you're preparing a camera-ready file for a print shop, "marginally different" is the kind of difference that becomes visible after you've paid for a press run.

## What the colophon records

The colophon of these volumes records more than the commit hash. It also captures the **build environment** at the moment of compilation:

- Hostname of the machine that ran the build
- Operating system
- LuaTeX version

This is not exotic instrumentation. It's a few lines of shell piped into LaTeX at build time — `hostname`, `uname -sr`, `luatex --version` — injected into a `revision.tex` file that gets `\input`-ted at compilation. The result is a colophon that can answer both *what source produced this?* and *where and how was it compiled?*

```latex
% revision.tex — generated by the Makefile, not hand-edited
\newcommand{\gitrevision}{a3f7c12}
\newcommand{\buildhostname}{buildserver-01}
\newcommand{\buildos}{Linux 6.8.0}
\newcommand{\luatexversion}{1.17.0}
```

## Why LaTeX versions silently shift output

LaTeX is not a fully deterministic system with respect to version. Between major TeX Live releases — and sometimes between minor ones — hyphenation patterns change, font metric handling changes, internal paragraph-breaking algorithms are adjusted. Any of these can alter line breaks. Altered line breaks change paragraph depths. Changed paragraph depths change page breaks. A book that ran to 136 pages at TeX Live 2022 may run to 137 at TeX Live 2024, and the difference will not announce itself with an error message.

This is why the project pins TeX Live 2023 in CI: not because 2023 is inherently better, but because a pinned version produces the same output on every run, on every machine, in every environment. The print shop receives a PDF that was produced by a known toolchain. If it ever needs to be reproduced, the same toolchain is available.

The build environment record in the colophon closes the traceability loop: source hash pins the content; toolchain version pins the rendering; hostname and OS document the physical environment. A reader holding the book can, in principle, reconstruct the exact conditions under which their copy was produced.

## What happens without this

The alternative is the common case: a PDF produced by "whatever LaTeX I had installed," with no record of when or how. If the layout ever needs to change, the question "does my current LaTeX version produce the same output as the original?" has no answer. If the page count was 136 when the print run was ordered and is 137 when the file is regenerated, nobody knows whether that's a source change or a toolchain drift.

For a one-off personal project, that ambiguity is manageable. For a project with multiple contributors, a CI pipeline, and a print shop waiting for a stable file, it's a latent failure mode.

## The build is part of the artifact

The deeper principle is that a printed book is not just its source — it's its source *as rendered by a specific environment*. Recording that environment is part of what makes the artifact reproducible rather than merely re-generatable.

Software teams understood this a long time ago: lock files, container images, and pinned dependency versions exist precisely because "it works on my machine" is not a deployment strategy. A LaTeX pipeline that produces print artifacts lives under the same constraint.

The commit hash in the colophon tells the reader what the source was. The toolchain record tells them what rendered it. Together, they make the artifact traceable — not in an archival sense, but in the practical sense of being able to answer the question a print shop or a collaborator will eventually ask: *can you reproduce this exactly?*

The answer, when the build environment is part of the record, is yes.
